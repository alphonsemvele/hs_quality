0. LOCKED ARCHITECTURE DECISIONS (reference — do not re-litigate)
================================================================================

Backend framework    : Laravel 12 (PHP 8.2+)
Web frontend         : Inertia + React + TypeScript + Tailwind v4 (admin users)
Mobile frontend      : React Native + offline-first SQLite (field intervenants)
API layer            : REST under /api/v1/* with Sanctum tokens (serves mobile)
Database             : PostgreSQL 16 (source of truth, ACID, JSONB, PostGIS-ready)
Cache / queue / pubsub: Redis 7
File storage         : S3-compatible with SSE-KMS encryption (AWS S3 or MinIO local)
Real-time            : Laravel Reverb (WebSocket server)
Hosting              : AWS France (Paris) or OVHcloud France — HDS-certified
Tenancy              : Row-level via BelongsToStructure trait + global scope
                       (PostgreSQL schema-based escape hatch preserved)
Testing              : Pest (NOT PHPUnit); feature + unit test per feature;
                       suite always green; cross-tenant leak test mandatory per
                       domain model
Auth                 : Session cookies for Inertia web; Sanctum tokens for API;
                       MFA mandatory for dirigeants / référents qualité /
                       coordinateurs; optional for intervenants
Security posture     : Top priority — multi-tenant isolation, audit logging,
                       encryption at rest, Form Requests, Policies on every
                       model, secrets in config (never env() in runtime code)
Ignored / rejected   : .blueprint and draft.yaml files in repo root (hospital
                       IS, NOT QualitéDomicile); hospital-domain tables
                       (patients, admissions, prescriptions, factures, etc.);
                       PHPUnit for new tests; custom-built multi-tenancy (use
                       stancl/tenancy patterns); multi-database tenancy as
                       default (row-level instead)

1. THE 12 ENGINEERING CONCERNS (mandatory — verified at every phase)
================================================================================

Every PR and every phase milestone is reviewed against these 12 concerns.

  1. Architecture & code organization
  2. Security (OWASP Top 10 + HDS/RGPD compliance)
  3. Database & data layer
  4. Multi-tenancy
  5. API design & contracts
  6. Performance & scalability
  7. Reliability & resilience
  8. Observability
  9. Background processing
 10. Testing strategy
 11. Deployment & operations
 12. Compliance, governance & team

Concerns 1–4 MUST be right from day one (Phase 0 + Phase 1 Month 1). The
rest are additive and mature over 36 months. Full detail in
feedback_backend_engineering_checklist.md.

4. PHASE 1 — MVP (4 months, target: 10 structures + 200 intervenants)
================================================================================

Per CDC §9: Traçabilité complète + Gestion incidents + Dashboard basique +
Application mobile offline. First structure pilote en production.

--------------------------------------------------------------------------------
Month 1 — Core entities + authentication UX
--------------------------------------------------------------------------------

Week 1–2  Bénéficiaires
  Domain:   beneficiaires table + Eloquent model (every field tenant-scoped)
  Columns:  structure_id, uuid id, nom, prenom, date_naissance, adresse,
            telephone, situation_familiale, gir (1–6), medecin_traitant,
            personne_reference_nom, personne_reference_telephone,
            notes_medicales (encrypted), allergies (encrypted),
            timestamps, deleted_at (soft delete)
  Model:    BelongsToStructure, Auditable, encrypted casts for medical fields
  Policy:   view/create/update/delete — tenant-checked, role-aware
            (intervenants see only assigned bénéficiaires; coordinateurs
             see all in their structure)
  Requests: StoreBeneficiaireRequest, UpdateBeneficiaireRequest
  Service:  BeneficiaireService — create, update, soft-delete, restore,
            anonymize (for RGPD erasure)
  Inertia:  list (with filter/search/sort), create, detail (tabbed: info,
            interventions history, plan d'accompagnement, incidents), edit
  Tests:    feature tests per endpoint, unit tests per service method,
            cross-tenant leak test

Week 3    Plans d'accompagnement
  Domain:   plans_accompagnement + taches_planifiees (recurring visit
            checklist with frequency per task)
  Logic:    a bénéficiaire has one active plan; a plan has many tâches
  Features: CRUD, templates (copy from another bénéficiaire's plan)
  Tests:    standard Pest coverage

Week 4    Intervenants management
  Domain:   extend users with intervenant-specific fields; create
            intervenant_beneficiaire pivot for assignment
  Features: list intervenants (coordinateurs see their structure's only),
            assign to bénéficiaires, intervenant profile with placeholders
            for habilitations + certifications (full M5 in Phase 2)
  Tests:    standard Pest coverage

  Month 1 acceptance: Coordinators can create structures, bénéficiaires with
  plans, and intervenants. Multi-tenant enforced everywhere. 50+ Pest tests
  green.

--------------------------------------------------------------------------------
Month 2 — M1 Traçabilité des interventions (web admin)
--------------------------------------------------------------------------------

Week 1–2  Interventions entity (the central table)
  Columns:  id uuid, structure_id, intervenant_id, beneficiaire_id,
            plan_accompagnement_id, date_prevue, heure_prevue_debut,
            heure_prevue_fin, heure_reelle_debut, heure_reelle_fin,
            latitude_checkin, longitude_checkin (PostGIS-ready), statut
            (planifiee/en_cours/realisee/annulee/manquee), mode_saisie
            (mobile/web/batch), rapport_texte (encrypted),
            rapport_voice_transcript (encrypted)
  Related:  intervention_taches_realisees (which tâches from plan were done),
            intervention_photos, intervention_signatures
  Service:  InterventionService — plan from tour, check-in, check-out,
            attach photo, attach signature, submit report, auto-cancel no-show
  Inertia:  today's tour view, intervention detail (tasks + photos +
            signature), history per bénéficiaire

Week 3    Photos & signatures
  Upload:   multipart endpoint → S3 with SSE-KMS encryption
  Validation: MIME/size (images only, max 5MB each)
  Display:  signed URL generation (expires in 1 hour)
  Signature: captured as base64 PNG → stored in S3 with restricted path
  Tests:    security-focused (path traversal, MIME spoofing, size limits)

Week 4    Intervention dashboard for coordinators
  UI:       list of today's interventions across all intervenants with
            status color coding, filter by intervenant/bénéficiaire/statut
  Real-time: update when intervention is checked-in or completed
             (Reverb broadcast — validates WebSocket setup early)

  Month 2 acceptance: Coordinators plan a tournée, see intervenants' progress
  in near-real-time, access full intervention history per bénéficiaire.
  Photos and signatures flow through S3. 100+ Pest tests green.

--------------------------------------------------------------------------------
Month 3 — M2 Incidents + M7 basic dashboard
--------------------------------------------------------------------------------

Week 1–2  Incidents + gravity algorithm
  Domain:   incidents, incident_actions_correctives, incident_suivis
  Enums:    categorie (chute/agression/erreur_médicamenteuse/
            maltraitance_suspectée/situation_danger/autre),
            gravite (mineur/significatif/grave/critique),
            statut (declare/en_analyse/plan_actions/clos)
  Service:  GraviteClassifier (pure function, 100% unit test coverage,
            takes incident inputs, returns gravité per CDC rules)
  Service:  IncidentService — declare, classify, assign to coordinateur,
            launch 5-whys workflow, close
  API:      POST /api/v1/incidents with StoreIncidentRequest + idempotency
            key, auto-classifies, broadcasts IncidentDeclared event
  Jobs:     NotifyResponsableSecteurJob (every declaration),
            NotifyARSJob (fires only if gravité in {grave, critique},
            sends structured email)
  Workflow: 5-whys UI (Inertia) + state machine in service layer
  Features: corrective actions CRUD + follow-up tracking

Week 3    M7 Basic dashboard
  Service:  DashboardStatsService — per-structure aggregation
  Cache:    Redis with tag structure:{id}:dashboard, 5-min TTL, invalidated
            on any write to interventions/incidents
  Metrics:  interventions this month, en cours, incidents declared,
            incidents en cours, conformity score (placeholder for P2),
            taux PAC (placeholder), QVCT moyen (placeholder)
  Views:    executive (synthetic KPIs, evolution charts for dirigeants),
            operational (today's work, alerts for coordinateurs)
  UI:       Inertia with Chart.js or similar

Week 4    Hardening + pilot dry run
  - Rate limit tuning based on observed traffic
  - Sentry monitored for 1 week; fix any uncaught exceptions
  - Load test (k6) simulating 200 intervenants × 5 interventions/day at
    peak concurrency; verify p95 < 500ms on dashboard
  - Run security-review Claude skill on the whole module
  - Book external pentester for Phase 1 end-of-quarter test
  - Staging walkthrough with product team

  Month 3 acceptance: Incidents declared on web (mobile not yet),
  auto-classified, auto-notified, tracked to closure. Dashboard loads
  < 500ms under realistic load. 200+ Pest tests green.

--------------------------------------------------------------------------------
Month 4 — Mobile API + React Native app + Pilot onboarding
--------------------------------------------------------------------------------

Week 1    Mobile API
  Routes:   /api/v1/auth/*, /api/v1/interventions/*, /api/v1/incidents/*,
            /api/v1/beneficiaires/*, /api/v1/sync/*
  Auth:     Sanctum personal access tokens with MFA-gated issuance for
            sensitive roles
  Resources: InterventionResource, IncidentResource, BeneficiaireResource —
             consistent JSON response shape
  Middleware: idempotency (reads Idempotency-Key header, checks Redis
              for stored response, replays or executes)
  Docs:     OpenAPI 3.0 auto-generated via Scramble, published internally
  Limits:   300 req/min per authenticated user, 30/min on login

Week 2    React Native app skeleton (mobile team)
  (Backend stays stable; mobile team consumes the API.)
  Features: auth with secure keychain storage, today's tour view,
            intervention detail (plan tasks, report entry, photo + signature
            capture), incident declaration form (< 2 minutes per CDC §4.2)
  Offline:  local SQLite schema mirroring server, offline queue, pending-sync
            indicator, auto-sync on reconnect

Week 3    Offline sync protocol hardening
  Server:   every write endpoint accepts both server-assigned and
            client-assigned UUIDs (offline mobile generates IDs before sync)
  Conflict: last-writer-wins for most fields; both writers preserved as
            notes for free-text reports with conflict markers
  Endpoint: POST /api/v1/sync/batch — accepts array of queued operations,
            processes in order, returns success/failure per operation
  Tests:    simulated offline scenarios (two intervenants edit same
            bénéficiaire offline, sync, verify resolution)

Week 4    Pilot onboarding
  - Deploy production environment (AWS Paris, HDS-certified configuration)
  - Seed 10 pilot structures via manual onboarding (real customers)
  - Train coordinators (2-hour session per structure)
  - Distribute mobile app to ~200 intervenants (internal TestFlight / Play)
  - Monitoring dashboards active; on-call rotation established
  - Feedback channel opened (Slack, Intercom, or phone line)

================================================================================

Goal: Ship Premium offering with predictive AI + beneficiary portal + sector
benchmark.

Deliverables:

  M9 IA prédictive
    Python microservice (scikit-learn + transformers + LLM API), exposed
    via REST initially, migrate to gRPC if call volume justifies.
    Predictions: burnout risk, autonomy loss detection, preventive action
    suggestions, semantic analysis of intervention reports.
    Integration: Laravel queues ML jobs, Python service consumes and
    writes results back to PostgreSQL analytics schema. Laravel reads
    results via standard Eloquent.
    Fallback: if Python service is down, predictions show "en calcul"
    placeholder — never error out the main flow.

  M8 Portail bénéficiaires
    New Inertia app (or Next.js PWA) for bénéficiaires and familles,
    separate auth, access to their care plan + intervention history +
    satisfaction survey + direct incident reporting. Anonymous tokens
    for family members (signed URL access with limited scope).

  Benchmark anonymisé
    The single approved CrossTenantQueryService usage: aggregate
    anonymized indicators across all structures of comparable size,
    publish monthly sector report. Every access logged and auditable.

  Reporting engine
    Annual quality report auto-generated per structure (PDF), sent to
    authorities as required.

Engineering concerns scaled:
  - Read replicas for dashboard / analytics workloads
  - Table partitioning enabled on interventions, audit_logs,
    qvct_reponses (by structure_id, date)
  - Caching matured (layered: Redis hot + CDN edge)
  - Contract tests run in CI against OpenAPI spec

Phase 3 acceptance:
  [x] 200 client structures
  [x] Premium offering live
  [x] First sector benchmark report published
  [x] Burnout predictions operational with measurable precision/recall

11. DEFINITION OF DONE (PER PHASE)
