A. WHAT QUALITéDOMICILE IS
================================================================================

QualitéDomicile is a multi-tenant SaaS for French home-care organisations
(SAAD — Service d'Aide et d'Accompagnement à Domicile, SSIAD — Service de
Soins Infirmiers à Domicile, SPASAD, ESAD, CCAS). Each subscribing
organisation is called a "structure". The platform has two frontends:

  1. Web admin (Inertia + React) — used by office staff: coordinateurs,
     dirigeants, référents qualité, RH, responsables formation.

  2. Mobile app (React Native, offline-first) — used by intervenants à
     domicile (field carers). REST API under /api/v1/* (not yet built).

The product must comply with:
  • RGPD (EU General Data Protection Regulation)
  • HDS (Hébergement de Données de Santé — French health-data hosting cert)
  • ANSSI security baseline
  • Référentiel HAS (Haute Autorité de Santé) quality criteria

Multi-tenancy model: Row-level isolation. Every domain table has a
structure_id foreign key. A BelongsToStructure Eloquent trait applies a
global scope that makes rows invisible to other tenants at query time.
There is no way to list, read, update, or delete another structure's data
through normal application code paths.

E. MODEL DESIGN — THE FOUR CORE M1 DOMAIN MODELS
================================================================================

The CDC product document describes a French home-care quality platform where
the central workflow is:

  A bénéficiaire (care recipient) receives care from one or more intervenants
  (field carers). Their care is governed by a plan d'accompagnement (care
  plan) consisting of individual tâches planifiées (planned tasks, e.g.
  "morning wash 30 min, daily"). Intervenants are formally assigned to
  beneficiaries to control who sees their data (RGPD principle of minimal
  access).

The four models implement this workflow in a layered security architecture:
  1. Row-level tenancy (BelongsToStructure global scope)
  2. RBAC via Policy + Permission (spatie/laravel-permission)
  3. Validated writes via Form Requests
  4. Business logic in Service classes (never in controllers)
  5. Immutable audit trail (owen-it/laravel-auditing)

────────────────────────────────────────────────────────────────────────────────
MODEL 1 — Beneficiary  (app/Models/Beneficiary.php)
────────────────────────────────────────────────────────────────────────────────

PURPOSE
  Represents a care recipient — the person at the centre of every workflow on
  the platform. Their identity, medical context, and care history are stored
  here. This is the highest-sensitivity data in the system (RGPD Art 9 special
  category — health data).

DATABASE TABLE: beneficiaries
  id                       UUID  primary key (HasUuids — no sequential IDs
                                 leaked to frontend; offline sync safe)
  structure_id             FK → structures (tenant anchor; mandatory)
  first_name               string
  last_name                string
  date_of_birth            date (nullable)
  gender                   enum (male / female / other / not_specified)
  address                  string (nullable)
  postal_code              string (nullable)
  city                     string (nullable)
  phone                    string (nullable)
  email                    string (nullable)
  marital_status           string (nullable)
  gir                      integer 1–6 (AGGIR autonomy scale; nullable)
  primary_doctor           string (nullable) — médecin traitant
  primary_doctor_phone     string (nullable)
  emergency_contact_name   string (nullable)
  emergency_contact_phone  string (nullable)
  emergency_contact_relationship  string (nullable)
  status                   enum (active / exited / deceased / erased)
  admitted_at              datetime (nullable)
  exited_at                datetime (nullable)
  medical_notes            text (ENCRYPTED at rest via Laravel cast)
  allergies                text (ENCRYPTED at rest)
  medical_history          text (ENCRYPTED at rest)
  current_treatments       text (ENCRYPTED at rest)
  is_erased                boolean default false (RGPD erasure flag)
  timestamps               (created_at, updated_at)
  deleted_at               (SoftDeletes — data not physically destroyed)

ELOQUENT TRAITS & INTERFACES
  • HasUuids         — auto-generates UUID v4 on create; route-model binding
                       uses UUID string, not integer
  • BelongsToStructure — adds StructureScope global scope; every query is
                         automatically filtered to the current tenant's
                         structure_id. A coordinator from Structure A cannot
                         accidentally load Structure B's beneficiaries.
  • Auditable        — every create/update/delete is logged to the audits
                       table with user_id, structure_id, old values, new
                       values, IP, user agent. Required by CDC §7 (traçabilité).
  • SoftDeletes      — deleting sets deleted_at; data remains in DB for
                       legal retention; restore() is available

ENCRYPTED CASTS
  The four medical columns use Laravel's 'encrypted' cast:
    protected function casts(): array {
        return [
            'medical_notes'       => 'encrypted',
            'allergies'           => 'encrypted',
            'medical_history'     => 'encrypted',
            'current_treatments'  => 'encrypted',
        ];
    }
  Encryption uses APP_KEY (AES-256-CBC) transparently. The values are
  unreadable in the PostgreSQL dump without the key. This satisfies RGPD
  Art 9 (special category data protection) and HDS hosting requirements.
  The decrypted values are NEVER sent to the Inertia/React frontend in
  the standard BeneficiaryResource — they only appear in the DossierResource
  which is guarded by log_sensitive_read middleware.

COMPUTED ATTRIBUTES
  • fullName()   → "$first_name $last_name"
  • initials()   → "F.L" from first + last name
  • getAgeAttribute() → integer age from date_of_birth (PHP Carbon)

RELATIONSHIPS
  • structure()         BelongsTo Structure
  • carePlans()         HasMany CarePlan (all plans)
  • activeCarePlan()    HasOne CarePlan (where status = 'active')
  • intervenantAssignments()   HasMany IntervenantAssignment (all history)
  • assignedIntervenants()     BelongsToMany User through
                               IntervenantAssignment (active only,
                               wherePivotNull('unassigned_at'))
  • allAssignedIntervenants()  BelongsToMany User through
                               IntervenantAssignment (full history)

POLICY — BeneficiaryPolicy (app/Policies/BeneficiaryPolicy.php)
  BasePolicy::before() runs FIRST on every method:
    It reads $model->structure_id and compares to $user->structure_id.
    If they differ → false (cross-tenant deny). This is a hard stop that
    cannot be bypassed by any other logic.

  viewAny  — requires beneficiaries.viewAny permission
  view     — coordinateurs/dirigeants: any in their structure
             intervenants: ONLY if there is an active IntervenantAssignment
             linking them to this specific beneficiary
  create   — requires beneficiaries.create permission
  update   — requires beneficiaries.update permission
  delete   — requires beneficiaries.delete permission
  restore  — requires beneficiaries.restore permission
  erase    — requires beneficiaries.erase permission (RGPD Art 17, hardest)

SERVICES — BeneficiaryService
  create(array $data, User $createdBy): Beneficiary
    • Wraps in DB::transaction
    • Stamps structure_id from current tenant
    • Returns ->fresh() to get all DB defaults

  update(Beneficiary $beneficiary, array $data): Beneficiary
    • Wraps in DB::transaction
    • Never allows structure_id to be changed
    • Returns ->fresh()

  anonymize(Beneficiary $beneficiary): Beneficiary
    • RGPD Art 17 erasure — replaces personal fields with anonymised values
    • Sets is_erased = true, status = 'erased'
    • Does NOT delete the record (legal audit trail must survive)
    • Cannot be undone

ACCESS CONTROL SUMMARY
  Who sees what:
  • coordinateur    — all beneficiaries in own structure
  • dirigeant       — all beneficiaries in own structure
  • referent_qualite — all beneficiaries in own structure (read-only)
  • rh              — basic profile only (no health data)
  • intervenant     — only beneficiaries they are actively assigned to
  • admin           — super-admin, all structures (for support only)

────────────────────────────────────────────────────────────────────────────────
MODEL 2 — CarePlan  (app/Models/CarePlan.php)
────────────────────────────────────────────────────────────────────────────────

PURPOSE
  The plan d'accompagnement (individualized care plan) is the document that
  governs how a beneficiary's care is delivered. Per the CDC §4, every
  beneficiary in an SAAD/SSIAD must have a signed care plan. The plan defines
  the care objectives (objectifs) and the concrete tasks (tâches planifiées)
  that intervenants must execute on each visit.

  A beneficiary has at most ONE active plan at any time. Previous plans are
  archived. The activate/archive lifecycle is tightly controlled.

DATABASE TABLE: care_plans
  id               UUID  primary key
  structure_id     FK → structures (tenant anchor)
  beneficiary_id   FK → beneficiaries
  title            string
  objectives       text (ENCRYPTED — may contain medical goals/prognosis)
  start_date       date (nullable)
  end_date         date (nullable)
  status           enum  draft | active | archived
  archived_at      datetime (nullable)
  archived_reason  text (nullable) — required by HAS quality criteria
  created_by       FK → users (nullable)
  timestamps
  deleted_at       (SoftDeletes)

STATUS LIFECYCLE
  draft → active   POST /care-plans/{id}/activate
                   CarePlanService::activate() atomically archives any
                   currently active plan for this beneficiary before
                   activating the new one. This is a DB::transaction to
                   prevent two plans being active simultaneously.

  active → archived  POST /care-plans/{id}/archive
                     Requires a non-empty reason string (CDC §4.3).
                     Sets archived_at + archived_reason + status.

  Any status → deleted  DELETE /care-plans/{id}
                        Soft delete. Restricted to dirigeant role.
                        (A plan is a legal document; only directors can delete)

IMMUTABILITY RULE — THE ARCHIVE FREEZE
  Once a care plan is archived, it becomes IMMUTABLE:
  • CarePlanPolicy::update() → false (403 on PUT /care-plans/{id})
  • PlannedTaskPolicy::create/update/delete → false (403 on task mutations)
  • PlannedTaskService::guardArchived() → HttpException(409)

  This is enforced at two layers (Policy + Service) so that even if one
  layer is bypassed, the other catches it. The CDC requires that archived
  plans serve as permanent historical records — they document the exact
  care that was planned and delivered during a past period.

COPY-AS-TEMPLATE
  POST /care-plans/{id}/copy creates a new DRAFT plan with the same title,
  objectives, and tasks for the same beneficiary. Cross-structure copies are
  rejected (HttpException 422) — a coordinator cannot copy a plan from
  another structure even with direct knowledge of the UUID.

ELOQUENT TRAITS
  • HasUuids, BelongsToStructure, Auditable, SoftDeletes (same as Beneficiary)

RELATIONSHIPS
  • structure()    BelongsTo Structure
  • beneficiary()  BelongsTo Beneficiary
  • tasks()        HasMany PlannedTask (ordered by task_order)
  • createdBy()    BelongsTo User (nullable)

COMPUTED METHODS
  • isActive()    → bool (status === CarePlanStatus::Active)
  • isArchived()  → bool (status === CarePlanStatus::Archived)

POLICY — CarePlanPolicy (app/Policies/CarePlanPolicy.php)
  • BasePolicy::before() handles cross-tenant denial first
  • view       — requires care_plans.view permission
  • create     — requires care_plans.create permission
  • update     — requires care_plans.update AND plan must NOT be archived
  • archive    — requires care_plans.archive AND plan must NOT already be archived
  • delete     — requires care_plans.delete (dirigeant role only)
  • copyTemplate — requires care_plans.create

────────────────────────────────────────────────────────────────────────────────
MODEL 3 — PlannedTask  (app/Models/PlannedTask.php)
────────────────────────────────────────────────────────────────────────────────

PURPOSE
  A planned task is one line item within a care plan. It represents a
  specific care activity that must be performed on each visit (e.g.
  "Morning wash — 30 minutes, daily, mandatory"). The set of tasks on
  a care plan forms the checklist that field intervenants will follow
  when delivering care. Tasks have an order (task_order) so coordinators
  can define the logical sequence of the visit.

DATABASE TABLE: planned_tasks
  id               UUID  primary key
  structure_id     FK → structures (tenant anchor; ALSO mirrored from parent)
  care_plan_id     FK → care_plans
  title            string (max 200 chars)
  description      text (nullable)
  frequency        enum  daily | weekly | monthly | on_demand | custom
  duration_minutes integer (nullable; 1–600 minutes)
  task_order       integer (display sequence within the plan)
  mandatory        boolean (default true — is this task required on every visit?)
  timestamps
  deleted_at       (SoftDeletes)

CRITICAL DESIGN: structure_id MIRRORING
  PlannedTask has its own structure_id column (required by BelongsToStructure
  trait). However, tasks are never created independently — they always belong
  to a CarePlan that already has a structure_id.

  The model has a booted() listener:

    static::creating(function (PlannedTask $task): void {
        if ($task->care_plan_id) {
            $plan = CarePlan::find($task->care_plan_id);
            if ($plan) {
                $task->structure_id = $plan->structure_id;
            }
        }
    });

  This runs UNCONDITIONALLY on every creating event. It means:
    a) You cannot create a task with a mismatched structure_id even if you
       try to pass one explicitly — the listener overwrites it.
    b) The task inherits its tenant identity from the plan, never from
       user input.

TASK ORDER
  PlannedTaskService::create() calculates task_order automatically:
    $data['task_order'] ??= ($plan->tasks()->max('task_order') ?? -1) + 1

  This means:
    • First task in a new plan → task_order = 0
    • Next task → max + 1
    • If you pass an explicit task_order, it is respected (allows insertion
      at a specific position)

  There is no reordering endpoint yet (planned for Phase 1 Month 2 along
  with the drag-and-drop UI). For now, order is append-only.

REPARENTING PREVENTION
  PlannedTaskService::update() strips two fields before updating:
    unset($data['care_plan_id'], $data['structure_id']);

  This prevents a malicious or buggy caller from moving a task to a different
  care plan or changing its tenant. A future moveTo() service method would
  handle legitimate cross-plan moves with explicit business validation.

ENUM: TaskFrequency
  Values (English code, French label in UI):
    Daily     → 'Quotidien'
    Weekly    → 'Hebdomadaire'
    Monthly   → 'Mensuel'
    OnDemand  → 'À la demande'
    Custom    → 'Personnalisé'

ARCHIVE IMMUTABILITY (see CarePlan section)
  Any attempt to create, update, or delete a task belonging to an archived
  plan is blocked at BOTH:
    1. PlannedTaskPolicy (returns false → 403 before the service is called)
    2. PlannedTaskService::guardArchived() (throws HttpException(409) as a
       second-layer backstop)

POLICY — PlannedTaskPolicy (app/Policies/PlannedTaskPolicy.php)
  • BasePolicy::before() handles cross-tenant denial first (reads
    task.structure_id and blocks if mismatched)
  • create  — checks $user->can('update', $task->carePlan) AND plan not archived
  • update  — same check
  • delete  — same check
  The 'update' permission on the parent plan is reused — managing the tasks
  of a plan is semantically "updating the plan", so no additional granular
  permission is needed.

────────────────────────────────────────────────────────────────────────────────
MODEL 4 — IntervenantAssignment  (app/Models/IntervenantAssignment.php)
────────────────────────────────────────────────────────────────────────────────

PURPOSE
  The assignment pivot table formally records which intervenants are
  responsible for which beneficiaries. This is not merely a many-to-many
  join — it is a time-stamped, audited, legally significant record.

  Per the CDC §3 (confidentialité des données bénéficiaires) and RGPD
  principle of minimal access:
    "An intervenant may only access the personal data of beneficiaries
    they are formally assigned to serve."

  Without an active IntervenantAssignment row, an intervenant CANNOT:
    • See the beneficiary in their list
    • Access the beneficiary's profile
    • Access the care plan or planned tasks
    • Log interventions against this beneficiary (Phase 1 Month 2)

DATABASE TABLE: intervenant_assignments
  id                   UUID  primary key
  structure_id         FK → structures (tenant anchor)
  user_id              FK → users (the intervenant)
  beneficiary_id       FK → beneficiaries
  assigned_by_user_id  FK → users (nullable; who performed the assignment)
  assigned_at          datetime (when the assignment was created)
  unassigned_at        datetime (nullable; when the assignment was closed)
  notes                text (nullable; reason for assignment, instructions)
  timestamps

  NOTE: NO SoftDeletes
  IntervenantAssignment deliberately has no deleted_at column. Every
  assignment and unassignment must remain permanently visible in the audit
  trail. If we soft-deleted assignments, the history of "which intervenant
  served this beneficiary during which period" could be obscured, which
  violates both RGPD record-keeping requirements and HAS quality audit
  criteria. Physical deletion is not possible; only closing (unassigned_at).

PARTIAL UNIQUE INDEX — PREVENTING DUPLICATE ACTIVE ASSIGNMENTS
  The migration adds:
    CREATE UNIQUE INDEX ON intervenant_assignments
      (user_id, beneficiary_id)
      WHERE (unassigned_at IS NULL);

  This is a PostgreSQL partial unique index. It means:
    • The same intervenant CANNOT be assigned to the same beneficiary twice
      while both assignments are active (unassigned_at IS NULL)
    • After an assignment is closed (unassigned_at set), a NEW assignment
      for the same pair is allowed (the old row's unassigned_at is no longer
      NULL, so it no longer conflicts)

  The service also enforces this at the application layer:
    IntervenantAssignmentService::assign() checks for an existing active
    assignment and throws HttpException(409) with a clear message if one
    exists, before attempting the INSERT (so the user gets a meaningful
    error, not a PostgreSQL unique constraint violation).

SCOPES
  active()   → where('unassigned_at', null)
  inactive() → whereNotNull('unassigned_at')

  These scopes are used extensively:
  • BeneficiaryPolicy::view() uses active() to gate intervenant access
  • BeneficiaryController::show() loads active + historical assignments
  • User::assignedBeneficiaries() uses active() via wherePivotNull

RELATIONSHIPS
  • structure()      BelongsTo Structure
  • intervenant()    BelongsTo User (using FK user_id)
  • beneficiary()    BelongsTo Beneficiary
  • assignedBy()     BelongsTo User (using FK assigned_by_user_id)

ASSIGNMENT WORKFLOW
  1. Coordinateur opens a beneficiary's profile page (GET /beneficiaries/{id})
  2. BeneficiaryController::show() calculates eligible_intervenants:
       Users in same structure, type=intervenant, not already actively assigned
       to this beneficiary
  3. Coordinateur selects an intervenant from the list, optionally adds notes,
     submits POST /beneficiaries/{id}/assignments
  4. AttachIntervenantRequest validates:
       • intervenant_id EXISTS in users table with same structure_id,
         type=intervenant, not soft-deleted
  5. AttachIntervenantRequest::authorize() checks:
       • $user->can('update', $beneficiary) — coordinateur or above
  6. AssignmentController::store() loads the intervenant User model and
     calls IntervenantAssignmentService::assign()
  7. Service creates the assignment row with assigned_at = now()
  8. Any page reload now shows the intervenant in the active list

  UNASSIGN WORKFLOW
  1. Coordinateur clicks "Mettre fin" on an active assignment
  2. DELETE /assignments/{id} hits AssignmentController::destroy()
  3. Policy check: IntervenantAssignmentPolicy::delete()
     → BasePolicy::before() confirms assignment.structure_id == user.structure_id
     → requires beneficiaries.update permission
  4. IntervenantAssignmentService::unassign() sets unassigned_at = now()
  5. The intervenant immediately loses access to this beneficiary's data
     (BeneficiaryPolicy::view() calls active() scope which excludes the
     now-closed assignment)

POLICY — IntervenantAssignmentPolicy (app/Policies/IntervenantAssignmentPolicy.php)
  • BasePolicy::before() handles cross-tenant denial first
  • delete — requires beneficiaries.update permission
    (ending an assignment is semantically "updating the beneficiary's team")
  • There is no 'view' method — assignment data is always accessed through
    the beneficiary or intervenant context, never listed standalone.

AUDIT TRAIL INTEGRATION
  IntervenantAssignment is Auditable, so every create (assign) and update
  (unassign, notes change) is logged to the audits table with:
    • old_values / new_values (shows when unassigned_at changed)
    • user_id (who performed the action)
    • structure_id (tenant context)
    • ip_address, user_agent
  This satisfies CDC §7.2 (traceability of data access and modification)
  and RGPD Art 30 (record of processing activities).

MONTH 2 — Interventions (M-TRACE)
  The central tracking table. An intervention is a visit record:
  who visited, when, for how long, what was done. Field intervenants

  This module ties the care plan to actual delivery. A PlannedTask

MONTH 2 — Incidents / Événements Indésirables (M-INC)
  An incident is any adverse event during care delivery:
  fall, medication error, behavioural episode, etc. Per HAS §4.2,
  all incidents must be recorded within 24h and reviewed within 72h.

  The existing IncidentController is a stub. Month 2 will replace it
  with the full domain model including:
  • Severity enum (minor / moderate / serious / critical)
  • Categorisation (fall, medication, behaviour, environment, other)
  • Status workflow (declared → under_review → resolved / escalated)
  • Mandatory escalation to ARS (Regional Health Agency) for serious events
  • Linked to beneficiary + intervenant + care plan

MONTH 3 — QVCT Baromètre (Qualité de Vie et Conditions de Travail)
  The QVCT survey module collects anonymous feedback from intervenants
  about their working conditions. Per CDC §6.1, structures must conduct
  at least two QVCT assessments per year.

  Model design: QvctSurvey (campaign) + QvctResponse (one per employee
  per campaign). Responses are anonymised at storage time — the link
  between respondent and response is never stored. Results are aggregated
  by dimension (workload, autonomy, relationships, environment, meaning).

MONTH 3 — Plans d'Amélioration Continue (PAC)

H. SECURITY ARCHITECTURE SUMMARY
================================================================================

Every write operation in the application goes through this chain:
  1. Tenant scope   — BelongsToStructure global scope makes cross-tenant
                      rows invisible (404, not 403, on cross-tenant access)
  2. Policy         — BasePolicy::before() checks ownership; named methods
                      check role/permission
  3. Form Request   — Input validation + authorization in authorize() method
  4. Service        — Business logic with DB::transaction; invariant checks
  5. Audit log      — Every create/update/delete logged automatically via
                      Auditable trait

No shortcuts exist. Every domain model has all five layers. The test suite
has mandatory cross-tenant leak tests for every model to ensure the global
scope cannot be bypassed.

HDS compliance checklist (from CDC):
  [x] Encrypted health data at rest (Laravel 'encrypted' cast on medical fields)
  [x] Audit trail on all health data reads and writes
  [x] Sensitive-data access log (log_sensitive_read middleware)
  [x] Multi-factor authentication (Fortify TOTP — mandatory for coordinateurs+)
  [x] Rate limiting on all auth endpoints
  [x] Security headers (HSTS, CSP, X-Frame-Options)
  [x] Row-level multi-tenancy (zero cross-tenant data leakage)
  [x] Soft deletes (data not destroyed; legal retention preserved)
  [ ] S3 SSE-KMS encryption (configured in env; not yet tested end-to-end)
  [ ] PostgreSQL audit extension (planned Phase 2)
  [ ] Data retention policy enforcement (planned Phase 2)
